# 版本号与更新日志规范

## 编号规则

可用版为 `YYYY.M.N`，基于它继续测试时为 `YYYY.M.N.T`。年份完整保留，不缩成26。

| 示例 | 含义 |
|---|---|
| `2026.10.11` | 2026年10月第11次可用更新 |
| `2026.10.11.1` | 基于该版本的第1次测试 |
| `2026.10.11.2` | 基于该版本的第2次测试 |
| `2026.10.12` | 验证后形成当月第12次可用更新 |
| `2026.11.1` | 进入11月，当月第1次可用更新 |

第三段不是日期，第四段不是可用更新序号。月份与序号不补前导零，序号从1开始，最大65535，以兼容Windows资源字段。“可用”不等于已成为稳定版，GitHub仍可标注公开试用。

## 测试与发布流程

1. 以当前可用版为基线，例如 `2026.10.12`，首次实际交付测试包为 `2026.10.12.1`，后续交付用 `.2`、`.3`。不复用已交付编号；仅源码检查、构建失败或重复运行自动测试不算新交付，不增加次数。
2. 用户确认可用并授权后，去掉测试后缀并递增可用序号，例如将 `2026.10.12.1`—`.3` 合并为 `2026.10.13`。不能因自动测试通过就自行升可用号或公开发布。
3. 下一轮测试从 `2026.10.13.1` 开始。换月后可用序号从1开始；以形成可用版本的年月命名，例如10月基线的测试在11月确认，则为 `2026.11.1`，日志注明来源。

本轮可用版本为 `2026.10.14`，合并已交付的 `2026.10.13.1`—`.5`，下一轮实际测试从 `2026.10.14.1` 开始。源码与打包检查完成不等于公开发布，实际公开状态见GitHub及验收记录。原 `2026.10.13` 于10月21日完成构建与验收、10月22日公开，历史日期不变。旧版本及无编号测试不重新编号，不改既有GitHub标签、附件或校验值；旧 `.0` 仅作为历史例外保留。

## 构建约定

- VERSION位于 `desktop/__init__.py`，窗口、托盘、指南和产物名使用同一版本；指南标注实际源码版本。
- 实际交付测试前，设置四段VERSION并同步指南，再运行 `python scripts/build_desktop.py --local-test`。脚本拒绝用三段可用号生成测试包。
- 确认可用且授权打包后，设置三段VERSION、同步指南及安装器AppVersion/AppNumericVersion，再运行正式构建。脚本拒绝用四段测试号打正式包，并检查安装器版本一致。
- Windows内部资源始终四段：`2026.10.12`对应`2026.10.12.0`；`2026.10.12.2`直接对应`2026.10.12.2`，不能生成五段版本。构建时间仍可辅助诊断，但不能代替测试序号。
- 安装目录、AppId、数据库schema和凭据名称不随编号改变，不重置学习资料。版本号不代替数据兼容检查，也不新增自动更新功能；比较年月/序号应按数字，不按字符串，测试号不表示下一可用版已发布。

## 日志约定

主 `CHANGELOG.md` 按可用版本倒序，每个可用版只出现一次，写最终新增、修复和升级事项。同一基线的测试归入其下级标题，不反复堆叠同名“未发布补丁”。以下只是格式示例，**不是实际交付记录**：

```markdown
## 2026.10.12 · 2026-10-21

### 测试迭代（基于本版，待合并）

#### 2026.10.12.1 · 日期
- 修改搜索说明；待验收。

#### 2026.10.12.2 · 日期
- 修复首次测试发现的问题；待验收。
```

形成 `2026.10.13` 后写最终行为，并注明“合并2026.10.12.1—.2”；基线版下只保留简短测试摘要和合并去向，不改测试归属，不让未完成测试覆盖已发布功能说明。

操作步骤放离线指南，详细发布说明放 `docs/releases/版本号.md`，环境和测试结果放验收记录。新制度之前的原始日志完整保留于 `CHANGELOG-legacy.md`，不补造旧测试编号。
